# Phase 9: Streaming Response Orchestration

## Overview
Phase 9 transitions the conversational engine from monolithic request-response generation to a low-latency, fully streaming pipeline. The primary goal is to drastically reduce Time-To-First-Audio (TTFA) by pipelining LLM output directly into incremental TTS generation.

## Key Concepts

### Provider-Independent LLM Streaming
The `LLMProvider` abstraction was extended to support server-sent events (SSE) streaming. Instead of waiting for the full LLM completion, the `StreamingResponseOrchestrator` consumes tokens as they are emitted by the LLM (e.g., vLLM).

### Sentence/Clause Assembler
Because our TTS engine (Chatterbox or dummy) synthesizes complete sentences with prosody, we cannot send individual words to the TTS provider. The `SentenceStreamAssembler` buffers incoming tokens and flushes them to the TTS queue only when a complete linguistic boundary is reached (e.g., a period, question mark, or newline).

### PREGENERATED / TEMPLATE / DYNAMIC Routes
Responses are categorized into routes to optimize latency:
- **PREGENERATED**: Static audio files cached in Redis (e.g., greetings). Lowest latency (sub-100ms).
- **TEMPLATE**: Semi-dynamic structures where parts are pre-recorded. (Future enhancement).
- **DYNAMIC**: Fully generated by the LLM and synthesized on-the-fly. This phase optimizes this route via streaming.

### LLM/TTS Ownership Boundary
To maintain strict architectural decoupling, the LLM service and TTS service are entirely unaware of one another.
- The LLM service strictly handles text generation.
- The TTS service strictly handles audio synthesis and pacing.
- The `ConversationTurnController` acts as the orchestrator linking the two.

### ConversationTurnController and Barge-In Cancellation
When a caller interrupts (VAD detects `SPEECH_START`), the `ConversationTurnController` is responsible for halting the current turn. It simultaneously invokes:
1. `LLMService.cancel()`
2. `TTSService.interrupt()`
3. `StreamingResponseOrchestrator.interrupt()`

Crucially, these cancellations run in parallel. If the TTS engine fails to interrupt, the LLM will still be cancelled, preventing "runaway" generation.

### Response Generation Invalidation
To prevent stale LLM chunks (generated before an interruption but delivered after) from being spoken, each turn is assigned a `ResponseGeneration` ID. The TTS engine drops any audio queued for an older generation.

### Stale Token / Chunk Rejection
The response orchestrator enforces strict boundary checks. Any partial sentence buffered during an interruption is immediately discarded, ensuring the AI does not speak half a thought when the caller speaks.

### Local Dummy TTS Limitation
While the system is fully capable of streaming text chunks to a dynamic TTS engine, the current local Docker environment runs a dummy TTS provider to avoid blocking the pipeline. Real, low-latency dynamic TTS requires a cloud-based endpoint or a robust local worker that supports incremental synthesis.

### Cloud Qwen3 Target
The architecture natively supports streaming from OpenAI-compatible endpoints. The local fallback targets Qwen2.5-1.5B (due to 4GB VRAM limits), but the production target is Qwen3-8B or higher for better reasoning capabilities.

### Latency Metrics and Verification Matrix
- **Time-To-First-Token (TTFT)**: ~300ms (vLLM benchmark)
- **Time-To-First-Audio (TTFA)**: TTFT + First Sentence Assembly Time + First Chunk TTS Synthesis Time.
- A comprehensive test suite (`test_generation.py`, `test_stream_assembler.py`, `test_turn_controller_independence.py`) verifies the matrix of success/failure cases for cancellation isolation.
